# How WideSend works

## Architecture and privacy

```text
Sender browser <====== encrypted WebRTC data channel ======> Receiver browser
      |                                                           |
      +---- WSS ---- Worker → session Durable Object ---- WSS -----+
                   pairing, encrypted signaling, fallback relay
```

- React/Vite frontend served by Worker Static Assets; all application assets are bundled locally. No third-party analytics, fonts, or tracking scripts.
- One Durable Object per opaque room hash, with hibernatable WebSockets. Session credentials, role, expiration, and relay credit counts are attached to live sockets. A small Durable Object storage record retains the paired credentials and original expiry for up to 24 hours, independently of socket lifetime; relay credit counts stay transient. File contents are not cached or written to a cloud database. When the admin dashboard is set up, a D1 activity database retains connection IPs, why each connection closed, refused connection attempts, pairing codes, and browser-reported filenames, sizes, hashes, and outcomes for 90 days; without the dashboard nothing is recorded. Workers Logs receive unexpected server errors only, without IPs or file details, for 3 days (see [admin.md](admin.md#diagnostics)).
- Shared links put the random six-character pairing code in the URL **fragment**, which is not sent in the initial HTTP request; the app removes the fragment from the current history entry after reading it. The browser then includes the code in its TLS-protected WebSocket handshake. The Worker checks it against the room hash and records it for the private admin dashboard, including before a receiver connects.
- SPAKE2 (RFC 9382, P256-SHA256-HKDF-HMAC) mutually confirms a fresh shared secret before any encrypted transfer messages. HKDF-SHA-256 derives directional AES-256-GCM traffic keys from that secret, never directly from the six-character code. Every pairing/reconnection creates fresh ephemeral keys. Session-bound, per-direction counters prevent nonce reuse and bounded replay windows reject repeated encrypted frames. Per-transfer non-exportable device signing keys and authenticated peer public-key pins stay in browser IndexedDB, allowing automatic resume without repeating trust in the short code. The transfer protocol encrypts file names, sizes, MIME types, signaling, acknowledgements, and content before relaying. Separate authenticated activity reports disclose the selected file metadata to the site owner.
- File ID and byte offset are authenticated inside each chunk. The receiver rejects invalid lengths/offsets, ignores duplicates, and acknowledges only after writing. Each source file is hashed incrementally with SHA-256. Completion requires all bytes, successful destination close, and a streaming read-back hash match on the saved file. Transport interruption can resend from the receiver’s written offset.
- Sender buffering is bounded by a 1 MiB unacknowledged window plus transport buffers. The relay permits frames up to 524,329 bytes (512 KiB payload plus authenticated header, nonce, and tag) only when both sockets advertise support. Other connections retain the 256 KiB frame limit. Peers exceeding 4 MiB of uncredited forwarded data per connection are closed.
- WebSocket upgrades require the same origin. Sender/receiver reconnect credentials are independent random 256-bit values, carried in the handshake protocol header rather than query parameters. Credentials are scoped to each session and pinned role.
- Direct connectivity uses Cloudflare’s public STUN endpoint. Failed or stalled direct transfers fall back to the encrypted WebSocket path. No separate TURN service is needed.

Cloudflare observes connection IPs, timing, sizes, room locators, credentials, and public key-exchange messages. The activity feature retains pairing codes and reported metadata for 90 days. For new SPAKE2 transfers, knowing the code or reading the activity database is **not enough to decrypt recorded file traffic**. The room hash still permits offline code enumeration, and the admin deliberately retains the code: someone who knows it can impersonate a device during initial pairing. After mutual confirmation, the locally pinned device key is also required on resume. The deployment serving the JavaScript remains trusted. Browser-profile compromise can expose local file data and use its keys. This integration has RFC-vector and adversarial tests but has not had an independent cryptographic audit; JavaScript does not guarantee constant-time execution or secret-memory erasure. See [SECURITY.md](../SECURITY.md) for the exact protocol, trust boundaries, and upgrade behavior.

Both pages must use the new version to establish a SPAKE2 transfer. Mixed versions show **Refresh WideSend on both devices to continue** and preserve saved progress. Refreshing a previous-version recovery record upgrades it in place, retaining its original code, expiry, and file checkpoint. Traffic encrypted before that upgrade retains its old security properties. New clients never fall back to code-derived encryption; existing old/old tabs can finish using their previous protocol. No new Cloudflare binding, secret, migration, or login setting is required.

The public transfer site requires no login. The optional admin dashboard is a separate Worker that requires Cloudflare Access or its own password (see [admin.md](admin.md)). Invitation secrets protect individual transfers. Avoid publicly advertising a personal deployment if you want to keep usage within your own free allowance.

## Reliability and free-tier limits

### Public-use protection

Protection is enabled by the normal `npm run deploy` command. It adds an `AbuseGuard` SQLite Durable Object and two native rate-limit bindings; no dashboard setup, CAPTCHA, extra login, or paid service is required.

| Limit                                                 | Default                                                |
| ----------------------------------------------------- | ------------------------------------------------------ |
| Unrecognized participant/code attempts per network    | 60 per minute; 1,000 per hour                          |
| New transfers per network                             | 200 per hour; 1,000 per day                            |
| New transfers across the site                         | 2,000 per day                                          |
| Simultaneously open transfer sessions per network     | 20                                                     |
| Simultaneously open transfer sessions across the site | 50                                                     |
| All connection attempts at each Cloudflare location   | 120 per network per minute; 1,200 site-wide per minute |
| Open share rooms per network / across the site        | 10 / 50 (separate from transfer sessions)              |

These defaults let a team behind one office address work all day. A site open to everyone should set stricter `vars.ABUSE_LIMITS`, as widesend.app does (20 attempts a minute, 250 an hour; 20 new transfers an hour, 100 a day, 500 across the site; 5 and 25 open transfers; 3 and 25 rooms). Edit `vars.ABUSE_LIMITS` and `ratelimits` in your [wrangler.jsonc](../wrangler.jsonc) (see [configuration.md](configuration.md)), then run `npm run deploy`. A network means a public IPv4 address or an IPv6 /64; people sharing Wi-Fi, a VPN, or a mobile carrier may share a limit. Only Cloudflare's authoritative connection IP is used, not a caller's forwarded-IP headers. The guard stores a hashed network identifier and short-lived session/credential reservations separately from the 90-day activity history. Counters reset at the end of their fixed window, starting with the first accepted use; they survive deployment and are cleaned up after expiration.

Previously admitted credentials bypass the unknown-participant budgets and don't consume another creation allowance. They still obey connection burst and simultaneous-session limits. Both ends of the same transfer count as one session per network, and replacing a socket doesn't take another slot. Closed connections release their reservation; abandoned reservations expire after 15 minutes. Active connections renew every five minutes, independently of file traffic, so a long direct or relay transfer keeps its reservation. Unpaired transfers expire after 20 minutes. All receivers of one code count as one session. An open completed-transfer tab still occupies a slot until closed or replaced with a new transfer.

A limited browser displays a short waiting message in its selected language and automatically retries after the server's cooldown. Existing paired transfer checkpoints remain available within the original 24-hour deadline. An unpaired code still expires after 20 minutes, even while waiting. These controls add no per-file size or bandwidth cap and don't inspect file contents. Activity writes also deduplicate logical reports across reconnects: one manifest, each file's fingerprints, and each status/route combination per participant. Denied admissions do not create activity records.

### Relay usage and admission budget

The admin **Health overview** includes relayed bytes, observed incoming WebSocket messages, estimated request units, and transfers declined for relay (each counted once per UTC day). Traffic uses the selected UTC period; the budget always shows today. Forwarded bytes are counted once and include public key exchange, encrypted signaling, encryption overhead, and retransmissions; direct file bytes never enter this counter. The Worker counts messages it handles, including control and rejected messages. Automatic heartbeat messages are excluded. Estimated units are observed messages divided by 20, not Cloudflare's account-wide usage or remaining quota. HTTP upgrades, internal RPCs, alarms, duration, database operations and other applications consume additional allowances.

`vars.RELAY_BUDGET` in `wrangler.jsonc` configures the safety threshold:

```json
"RELAY_BUDGET": { "dailyRequestUnits": 50000, "stopNewAtPercent": 80 }
```

The default closes admission for **new relay transfers at 40,000 estimated units** (800,000 observed messages). This is roughly 98 GiB of large batched file traffic before control traffic and retries; it is not a byte cap or a throughput guarantee. The 50,000-unit planning budget leaves some allowance for admitted sessions, and additional headroom below Cloudflare's free request allowance. Admitted relay sessions continue through reconnects and UTC rollover until their original expiry, so their traffic can exceed the budget. The budget is an early admission cutoff, **not a hard spending/quota guarantee**. It resets at 00:00 UTC. Change the settings and run `npm run deploy`; no extra token, service, or login configuration is needed.

Updated browsers ask the Worker before using relay for files. A declined relay waits automatically, retains its pairing, and can still use an available direct connection. File and control ciphertext have a one-byte envelope on the browser-to-Worker hop, negotiated with `relayPolicy: 1`; the Worker strips it before forwarding. The payload remains authenticated and encrypted. Controls retain a bounded 1 MiB allowance per connection before also requiring relay admission. Legacy clients cannot distinguish file/control traffic, so they require relay admission for forwarded binary traffic; when the budget is closed, reload both pages to use the updated direct-only waiting behavior. This envelope negotiation is separate from encryption: new clients require a Worker and peer that support key-exchange version 2.

Per-connection cumulative counters are retained in WebSocket attachments, with no per-frame database write. They flush during activity about every 30 seconds or 512 messages, at terminal reports and disconnects, and during five-minute session maintenance. Quiet sessions can lag by five minutes; outages or abruptly lost sockets can leave gaps. Duplicate/out-of-order reports use high-water marks, so retries don't double-count usage. The guard stores daily aggregates for 90 days, per-connection deduplication counters for the current and previous UTC day, and relay admissions only until the original session expiry. File contents are never stored.

### Activity cleanup

Activity older than 90 days remains hidden from all admin queries. Cleanup now runs **hourly** (`17 * * * *`), deleting file and connection rows in bounded batches before deleting their transfer records. Each invocation uses a lease to prevent overlapping jobs, at most 42 D1 statements, and approximately 2,000 database row writes including indexes/status. A large transfer's child rows cannot trigger an unbounded cascading delete. Unfinished batches continue at the next run.

Health shows the last successful run, rows written, transfer records removed, expired records remaining and the oldest expired transfer. A 500-transfer backlog with file and connection metadata is covered by the database regression tests and clears within a day's scheduled runs. Very large metadata volumes, exhausted database allowances or failed jobs can still delay deletion and appear as a backlog; a free database cannot guarantee arbitrary retention workloads. The first status appears after the next hourly run following deployment.

These limits reduce abuse; they are not a guarantee against exhausting the free plan. A distributed flood still consumes Worker requests, and substantial legitimate relay traffic still consumes Durable Object allowances. Cloudflare's native rate-limit bindings are approximate and local to each Cloudflare location; the Durable Object guard supplies the exact shared counters and capacity checks. See [Cloudflare's rate-limit binding documentation](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

Direct data traffic avoids the Worker relay. When relay is needed, Durable Object request/message and active-duration quotas apply. The free plan has finite daily allowances; exhausted quotas can interrupt relay or signaling. There is no paid service automatically enabled by the app.

Updated browsers use relay batches only after the Worker confirms support and the receiver advertises it in an encrypted `ready` message. If batching support is omitted, compatible version-2 peers use 32 KiB chunks; encryption is never downgraded. Each batch has one AES-GCM tag authenticating its entire payload, file ID, and initial offset. The receiver validates the complete batch before writing, then writes 32 KiB at a time and acknowledges once per batch. It preserves the original disk checkpoint policy (at least every 1 MiB, at the next chunk after one second, and at file end). A resumed batch can start at any valid 32 KiB offset; duplicate prefixes are skipped. Small relay buffer credits are combined and flushed within 50 ms, while full-batch credits return promptly. Pending credits are discarded on socket or peer replacement, and the Worker resets the surviving socket's outstanding counter for its new peer.

For large, uninterrupted relayed files, batching reduces file-related incoming messages from about 81,920/GiB to at most about 8,192/GiB before setup, retries, diagnostics, and other account usage. Using Cloudflare's documented 20:1 incoming WebSocket message ratio, this is roughly 410 request units/GiB instead of 4,096. It is a message-budget estimate, not a bandwidth guarantee: duration, database quotas, and network/device speed still matter. No new byte quota or file-size cap is imposed. See [Durable Object pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/).

Worker restarts, deploys, or network loss can close connections. The browsers reconnect using their session credentials and exchange the receiver’s written offset. The Durable Object storage record preserves the paired participants when all sockets disappear. Page refresh or browser restart restores the local journal and receiver checkpoint; the sender may need to reselect its original files. The original expiry is never extended by reconnecting.

Both devices must be able to reach the deployment over HTTPS/WebSocket. Direct WebRTC is an optimization, not a prerequisite. Networks blocking the deployment itself cannot be bypassed by the relay.
